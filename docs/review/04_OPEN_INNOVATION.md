# DRIVELOG 평가서: 4. 오픈이노베이션 심사위원 (창의성·문제 정의)

평가일: 2026-11-06. 프롬프트: [EVALUATION_PROMPT.md](EVALUATION_PROMPT.md)

## 1. 한 줄 총평
차 안에서 끝나는 개인정보 보호형 드라이브 카드로 잘 다듬었지만, 풀려는 문제가 문서에 없고 처음의 독창적 서사(부산 바다 3곳 목표)를 걷어내면서 "Strava 카드의 차량판"으로 보일 위험이 크다.

## 2. 담당 관점 점수: 5.6 / 10
평범(5~6) 구간 위쪽이다. 시연 장면 하나만 살리면 상위 10팀 경쟁권(7)까지 오를 수 있다.

## 3. 공모전 4개 항목 (내 관점)
- 차량특화성 6.5: 기어 P 잠금, 내비 위임, 도착 TTS가 기록 흐름에 묶여 있다(`CarViewModel.kt:179-202`, `Recorder.kt:169`). 다만 결과물인 카드 자체는 휴대폰으로도 만들 수 있다.
- 창의성 5.0: 카드, 구간 기록, 경로 다시 보기는 NRC·Strava에 이미 있다. 새로운 것은 QR `#` 전달 방식뿐이다.
- 기술 활용성 6.5: NaviHelper 검색·경로·개요 화면, FusedLocation 근접 알림(`PleosCarPlatform.kt:382`), TTS를 핵심 흐름에 썼다.
- 사업성 3.5: 타깃, MAU, Retention 근거가 저장소에 없다(README, docs 전체 검색 결과 없음).

## 4. 강점
1. **개인정보를 지키는 QR 전달.** 경로를 encoded polyline으로 URL의 `#` 뒤에 담아 서버 없이 휴대폰으로 넘긴다(`CardShare.kt:65-85`). 휴대폰 페이지는 이미지 저장까지 된다(`web/card/index.html:185-194`). 이 저장소에서 가장 독창적인 지점이다.
2. **안전 제약을 경험 설계로 바꿨다.** 주행 중에는 장소, 분, 거리만 보이고, 감정에 호소하는 연출은 정차 후로 미뤘다. 주행 중 화면 제한 원칙을 따르면서 "도착 후의 보상"을 만든다(`PLEOS_DESIGN_PRINCIPLES.md` §2, `CarMotion.kt`).
3. **카드 문구가 감성적이다.** "○○에 남긴 하루"(`CarScreens.kt:567`), 경로 다시 보기(`CarScreens.kt:584`, `DriveRouteArt.kt:133`). 숏폼 소재로 쓸 만하다.
4. **범위 정리를 했다.** 커뮤니티와 휴대폰 미리보기는 debug 전용이고(`CarApp.kt:44,95,129`), 서버는 플래그로 꺼 두었다.

## 5. 약점과 위험
1. **[치명] 문제 정의 부재.** 누구의 어떤 불편인지 적힌 문서가 없다. 설계 원칙 문서 §10이 PRD를 인용하지만 PRD 파일은 저장소에 없다. 서류심사는 Pain Point를 필수로 본다.
2. **[높음] 차별점 약화.** "장소 3곳 목표"를 삭제했다(설계 원칙 §10, F01). 남은 카드, 구간, 다시 보기는 기존 활동 앱과 같은 구조다. 문서도 벤치마크를 NRC·Strava로 명시한다(§5).
3. **[높음] 시연 자료가 현재 앱과 다르다.** 시연 영상이 없다. 남은 화면 자료(`docs/verification/mockup-ui/p17-complete.png`, 11-03)는 삭제된 3곳 흐름과 흑백 사진을 보여 준다.
4. **[높음] 결정적 장면이 배포 조건에 달려 있다.** QR은 `cardWebUrl`로 빌드했을 때만 나온다(`CarApp.kt:47`, `app/build.gradle.kts:21`). 카드 페이지를 호스팅했다는 흔적이 없다.
5. **[보통] 심사위원 재현 장벽.** release에는 시뮬레이션이 없어 `demo-drive.ps1 -Prepare`부터 2단계 절차를 거쳐야 카드가 나온다(README "주행 재현").
6. **[보통] 사진 저작권과 흑백 배너.** 사진 출처가 미확인이고(README "남은 작업"), 배너 3종은 흑백이다(설계 원칙 §5).
7. **[낮음] 화면 수가 많다.** Screen이 19종이다(`CarViewModel.kt:33`). release에서는 줄지만 코드상 핵심이 분산되어 있다.

## 6. 마감 전 우선순위
1. 문제 정의 1쪽을 README 맨 위에 둔다. 페르소나 1명, Pain 2개, 해결 방식을 적는다. 효과 최대, 2시간.
2. 카드 페이지를 GitHub Pages에 올리고 그 주소로 제출 APK를 빌드한다. QR이 실제로 동작해야 한다. 효과 높음, 2시간.
3. 시연 영상 90초를 만든다. 효과 높음(가산점과 서사), 4~6시간.
4. "왜 차에서인가"를 한 문단으로 쓴다. 휴대폰 없이 기록 시작부터 카드까지 이어지는 흐름, 정차 후 보상 구조를 담는다. 1시간.
5. 흑백 배너를 교체하고 사진 출처를 정리한다. 2시간.
6. verification 화면 자료를 현재 흐름으로 다시 찍는다. 1시간.

## 7. 2차 PT 예상 질문
1. **"티맵 주행 기록이나 Strava와 무엇이 다른가?"**
   방향: 차 안에서 끝난다는 점을 앞세운다. 기록 시작은 탭 2번이고, 내비에 위임하고, 서버 없이 QR로 전달한다. 기능 수가 아니라 운전자 주의 분산 0을 차별점으로 제시한다.
2. **"매일 출퇴근하는 사람도 이 앱을 여는가?"**
   방향: 반복 사용 대상이 아니라고 인정한다. 여행과 주말 드라이브라는 타깃을 숫자와 함께 좁히고, 누적 기록과 코스 공유 확장 계획을 보인다.
3. **"3분 시연의 '와' 장면은 무엇인가?"**
   방향: P로 바꾸는 순간 경로가 카드 위에 그려지는 장면, 이어서 휴대폰으로 QR을 찍어 같은 카드를 저장하는 장면을 끊김 없이 한 번에 보인다.

## 8. 확인하지 못한 것
- 실제 화면 상태: 빌드와 설치를 하지 않았고, 현재 흐름의 화면 자료도 없다.
- QR 카드 페이지의 실제 휴대폰 동작: 호스팅 주소가 없다.
- PRD와 기획서 원문: 저장소에 없다.
- 공모전 아이디어 특별상과 숏폼 챌린지의 세부 기준: 프롬프트에 포함되지 않았다.
