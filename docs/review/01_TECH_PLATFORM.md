# DRIVELOG 평가서: 1. Pleos 플랫폼 기술 심사위원

평가일: 2026-11-06. 프롬프트: [EVALUATION_PROMPT.md](EVALUATION_PROMPT.md)

## 1. 한 줄 총평
Pleos SDK 5종과 AAOS Car API를 실제 핵심 흐름(찾기 → 안내 → 기록 → 도착/정차 저장)에 연결했고, 예외 처리와 에뮬레이터 실측 기록도 출품작 중 상위 수준입니다. 다만 심사위원이 실제로 실행할 release APK는 Pleos 에뮬레이터에서 검증한 기록이 없고, 차량 고유 데이터(Odometer)는 사실상 쓰이지 않습니다.

## 2. 담당 관점 점수: 7.8 / 10
상위 10팀 경쟁권(7~8)에서도 위쪽입니다. release 실측 기록만 채우면 수상권 진입을 노릴 수 있습니다.

## 3. 공모전 4개 항목 (기술 관점)
- 차량특화성 7.5: 기어와 UX 제한으로 화면을 잠그고, P 진입·안내 종료·도착 신호로 저장합니다(`CarViewModel.kt:172-206`). 다만 차량 신호는 기어 하나뿐입니다.
- 창의성 6.0: 기술적으로 새로운 것은 QR `#` 전달(서버 없이 휴대폰으로 넘김) 정도입니다.
- 기술 활용성 8.0: NaviHelper 9종 호출, FusedLocation 근접 알림, TTS·STT ON_DEVICE와 오디오 포커스를 씁니다(`PleosCarPlatform.kt:78-470`).
- 사업성 4.5: 서버와 동기화가 꺼져 있어 기술적으로 확장할 근거가 코드에 없습니다(`app/build.gradle.kts:17`).

## 4. 강점
1. **API 선택이 정확하고 근거가 남아 있습니다.** 기어는 AAOS `GEAR_SELECTION`으로 받고(SDK 기어 호출은 deprecated), 주행 판정은 `CarUxRestrictions`로 합니다. 상태를 모르면 잠금으로 처리하고(`VehicleStateMonitor.kt:24,41-78`), 연결이 끊기면 detach합니다.
2. **NaviHelper의 실제 동작을 직접 확인해 반영했습니다.** `onRouteEnded`는 안내 종료 신호가 아니어서 쓰지 않습니다(`PleosCarPlatform.kt:110`). 내가 보낸 새 경로가 기존 안내를 취소하는 경우를 구분하고(`:64,106-108`), 분할 화면에서는 `getDestinationInfo`를 다시 호출합니다(`:97`). 근거는 API 가이드 §13입니다.
3. **서비스 유무를 런타임에 확인합니다.** `serviceExists`, `onFailed`일 때 `dropNavi`(`:133-170`)를 거치고, 앞 화면일 때 1분간 재연결합니다(`CarViewModel.kt:220-229`). 서비스가 없으면 그 기능만 숨깁니다.
4. **기록 신뢰성 설계가 좋습니다.** 좌표를 받을 때마다 flush하고, 250km/h를 넘는 이동은 버리며, 위치가 끊기면 다시 요청합니다(`Recorder.kt:134-137,156,160`). 비정상 종료 후 마지막 줄이 깨져도 건너뛰고 복구합니다(`:214-235`). Back은 `moveTaskToBack`입니다(`MainActivity.kt:124`).
5. **STT를 운전 맥락에 맞게 다뤘습니다.** 듣기 제한 시간을 `onReady`부터 세고, 엔진 준비 지연은 20초까지 기다립니다. 결과는 검색창에만 넣습니다(`PleosCarPlatform.kt:209-275`, `CarViewModel.kt:157-163`).

## 5. 약점과 위험
1. **[높음] release APK의 Pleos 실측 기록이 없습니다.** §13의 주행·카드 검증은 모두 "debug 빌드"입니다. `apk/` 폴더도 없습니다. `docs/verification/RESULTS.md`는 Phase 1 기록이라 "DO 미선언, Pleos 에뮬레이터 미설치"라고 적혀 있어 현재 상태와 모순됩니다.
2. **[높음] Odometer를 사실상 쓰지 않습니다.** 에뮬레이터에서 값이 0.0이고, 모든 기록이 `GPS_ESTIMATED`로 저장됩니다(§13). 결국 휴대폰 GPS 앱과 차이가 기어 하나뿐입니다(`Recorder.kt:63-68`).
3. **[보통] 위치 지원 여부를 앱 시작 때 한 번만 판정합니다.** `locationSupported`는 ViewModel 생성 시 한 번 정해집니다(`CarViewModel.kt:116`). 부팅 직후 Fused 서비스가 늦게 올라오면 release에서 "기록할 수 없어요"가 계속됩니다. 재시도가 없습니다.
4. **[보통] release에서 outbox가 계속 커집니다.** 토큰이 없어도 기록마다 경로 전체를 outbox에 복제하고(`JourneyStore.kt:108-113`), 상태가 바뀔 때마다 JSON 전체를 메인 스레드에서 다시 씁니다(`:70-80`). 기록이 쌓일수록 지연과 용량이 늘어납니다.
5. **[보통] release에도 진단 화면이 열립니다.** 제목 길게 누르기가 빌드 구분 없이 연결되어 있습니다(`CarApp.kt:126`). 진단 화면은 별도의 NaviHelper·Fused 인스턴스를 만들고(`PleosDiagnosticsScreen.kt:34`), Pleos 토큰이 아닌 Material 기본 UI를 씁니다.
6. **[낮음] 연결 후 서비스가 죽는 경우를 처리하지 않습니다.** NaviHelper 연결 뒤 서비스가 죽어도 `naviConnected`가 true로 남습니다. TTS 초기화가 실패하면 다시 시도하지 않습니다(`PleosCarPlatform.kt:153-186`).
7. **[낮음] 테스트가 순수 로직에만 있습니다.** 단위 테스트는 47개이며 `Recorder`, `JourneyStore`, `CarPlatform`을 가짜로 바꿔 쓴 테스트가 없습니다. 계측 테스트는 예제뿐입니다. `server/`는 제출 범위 밖이고 README도 "모바일 웹이 목표 기준"이라고 적고 있어 득이 거의 없고, 심사위원의 혼란만 부릅니다.

## 6. 마감 전 우선순위
1. release APK를 Pleos 2.1.0에 새로 설치해 README 흐름 전체를 실측하고, 결과를 RESULTS.md에 새로 씁니다. 실격 위험을 제거합니다. 3시간.
2. 진단 진입을 `BuildConfig.DEBUG`로 막습니다. 반려·혼란 위험을 줄입니다. 0.5시간.
3. `locationSupported`를 기록 시작 시점에 다시 판정합니다. 기록 불가 위험을 없앱니다. 1시간.
4. `phoneLinkEnabled=false`이면 outbox에 넣지 않습니다. 성능과 용량을 지킵니다. 1시간.
5. Recorder 복구와 FakeCarPlatform으로 안내 종료·저장 흐름을 테스트합니다. 기술 신뢰도를 높입니다. 3시간.
6. `server/`가 확장용임을 README 맨 위에 밝히거나 별도 브랜치로 옮깁니다. 0.5시간.

## 7. 2차 PT 예상 질문
1. **"DO를 선언했는데 카테고리 승인이 나지 않으면?"** 답변 방향: 기록은 포그라운드 서비스에서 계속되므로 화면이 잠겨도 기능은 유지된다는 점을 보이고, 정차 시 저장 흐름을 시연합니다.
2. **"Odometer가 0이면 차량 앱으로서의 가치는?"** 답변 방향: ±25% 교차검증 설계, UX 제한 연동, 내비 이벤트 기반 자동 저장이 휴대폰 앱에서는 불가능하다는 점을 설명하고, 실차에서 들어올 값의 경로를 보입니다.
3. **"내비가 앞에 있는 동안 콜백이 오지 않을 때 기록이 누락되지 않나?"** 답변 방향: 위치는 포그라운드 서비스로 계속 받고, 콜백은 복귀 시 몰아서 처리하도록 설계했으며(§13), 5.5km 실측과 복구 시험 결과로 답합니다.

## 8. 확인하지 못한 것
- release APK가 실제로 동작하는지: 빌드와 설치가 금지되어 있고, 해당 기록도 없습니다.
- §13의 실측 수치(CPU 0.45% 등): 원본 로그가 저장소에 없어 문서만 근거로 했습니다.
- 서버 테스트의 통과 여부: 실행하지 않았습니다.
- STT·NAVI 퍼미션의 App Market 승인 상태: 외부 확인 사항이라 확인할 수 없었습니다.
