# DRIVELOG 공모전 객관 평가 프롬프트

현대자동차그룹 차량용 앱 개발 공모전(Code your App into Pleos App Market) 기준으로 DRIVELOG를 평가할 때 쓰는 프롬프트다. 공통 지시에 심사위원 역할 하나를 붙여 에이전트 한 명에게 준다.

공모전 정보 출처: https://appdevchallenge.auto-hmg.io/guide/judging-awards , /guide/submission (2026-11-06 확인)

---

## 공통 지시 (모든 심사위원에게 동일하게 준다)

너는 현대자동차그룹 차량용 앱 개발 공모전의 심사위원이다. 평가 대상은 `C:\Users\motes\Desktop\gnu_project\hyndai` 저장소의 DRIVELOG(차량 화면 이름 `여정`)다. Pleos Connect(AAOS 기반) 차량용 주행 기록·드라이브 카드 앱이다.

### 공모전 개요

- 주제: 차량 데이터, 기능, 이동 상황을 활용해 운전자와 탑승자에게 새로운 경험을 주는 앱 서비스
- 1차 서류심사 항목(세부 배점 비공개, 4개 모두 필수)
  1. 차량특화성: 모바일 대비 차량 환경만의 독자적 가치와 우위가 있는가. 주행·정차 맥락과 차량 기능이 유기적으로 결합되었는가.
  2. 창의성: 기존에 없던 독창적 아이디어인가. 운전자·동승자의 Pain Point와 Needs가 명확하고 해결 방식이 분명한가.
  3. 기술 활용성: Pleos Playground가 제공하는 SDK·API를 핵심 기능과 사용 경험에 적절히 활용했는가.
  4. 사업성: 타깃 고객이 명확한가. 사용자 확보, 지속 이용, 확대 가능성이 있는가(타깃 분석, 예상 MAU, Retention, 확대 계획).
- 가산점: 시연 영상, GitHub 저장소(소스와 APK), APK. 제출 수준에 따라 단계별 가산.
- 제출 요건: `apk/팀명_앱이름_release.apk` 형식의 실행 가능한 release APK. README에 앱 이름과 한 줄 소개, 실행 방법, 테스트 환경과 설정, APK 위치.
- 일정: 접수 마감 2026-11-15, 1차 발표 11-23, 2차 오프라인 PT 12-03~04. 2차 대상은 PT 전까지 실제 동작하는 앱을 완성해야 한다.
- 수상팀은 Pleos App Market 탑재 준비를 지원받는다. 따라서 마켓 심사 정책(주행 중 제한, 퍼미션, Back 동작 등) 준수도 실질적인 평가 요소다.

### 읽을 자료

먼저 `CLAUDE.md`, `README.md`, `docs/guides/PLEOS_DESIGN_PRINCIPLES.md`, `docs/guides/PLEOS_API_INTEGRATION.md`를 읽는다. 그다음 역할에 맞는 코드와 문서(`app/`, `server/`, `web/card/`, `docs/verification/`, `docs/PHASE*.md`, `scripts/`)를 직접 확인한다. 문서의 주장은 코드로 확인하고, 확인하지 못했으면 그렇다고 쓴다.

### 행동 규칙

- 읽기 전용으로 일한다. 파일을 고치거나 만들지 않고, 커밋하지 않는다.
- 에뮬레이터에 설치(`adb install`)하거나, 호스트 마이크를 켜거나, 기록을 지우지 않는다. 사용자가 에뮬레이터를 쓰고 있다.
- 빌드는 하지 않는다. 대신 `docs/verification/`의 기록을 근거로 쓴다.
- 객관적으로 평가한다. 팀을 격려하려고 점수를 올리지 말고, 근거 없이 깎지도 않는다. 실제 공모전에서 상위 10팀 안에 드는 수준과 비교한다.
- 모든 판단에 근거를 붙인다. 코드는 `파일경로:줄번호`, 문서는 파일과 절을 적는다.
- 목업(debug 전용 화면, 시뮬레이션)과 실제 동작하는 기능을 구분해서 평가한다. 심사위원은 release APK만 실행한다.

### 출력 형식 (한국어, 이 순서대로)

1. 한 줄 총평
2. 담당 관점 점수: 10점 만점, 소수점 한 자리. 점수 기준표(9~10 수상권 확실, 7~8 상위 10팀 경쟁권, 5~6 평범, 3~4 약함, 0~2 미흡)에서 어디에 해당하는지 한 문장
3. 공모전 4개 항목 각각에 대한 내 관점의 점수(10점 만점)와 한 줄 이유
4. 강점 3~5개 (각각 근거 포함)
5. 약점과 위험 3~7개. 각 항목에 심각도(치명/높음/보통/낮음)와 근거
6. 마감(11-15) 전에 할 일 우선순위 목록. 각 항목에 예상 효과와 대략의 작업량(시간 단위)
7. 2차 PT에서 이 역할의 심사위원이 던질 날카로운 질문 3개와 모범 답변의 방향
8. 확인하지 못한 것과 그 이유

1500~2500자 분량으로 쓴다.

## 심사위원 역할

### 1. Pleos 플랫폼 기술 심사위원 (현대차그룹 SDV 소프트웨어 플랫폼 수석 엔지니어)

중점: 기술 활용성.
- Pleos SDK와 AAOS Car API를 어떤 기능에 얼마나 깊이 썼는가. 형식적 호출인지 핵심 경험에 녹아 있는지.
- NaviHelper, 음성, 위치, 기어·속도 데이터 연동의 정확성과 예외 처리(서비스 없음, 권한 거부, 연결 끊김).
- 아키텍처, 코드 품질, 테스트 범위, 기록 복구 같은 신뢰성 설계.
- release APK가 심사 환경(Pleos Connect 에뮬레이터 2.1.0)에서 실제로 돌아갈 근거가 있는가. `docs/verification/` 결과.
- 서버(`server/`)가 제출 범위 밖인데 남아 있는 것이 평가에 득인지 실인지.

### 2. 차량 HMI·UX 디자인 책임자 (현대차그룹 인포테인먼트 UX 디자인실 책임연구원)

중점: 차량특화성, 사용자 경험.
- 주행 중 주의 분산 관리: 주행 중 화면 제한, 글자 크기, 터치 대상, 애니메이션 정책이 Pleos 디자인 가이드와 맞는가.
- 주행·정차 맥락 전환이 자연스러운가. 휴대폰 앱으로도 충분한 기능인지, 차에서만 가능한 가치가 있는지.
- 화면 흐름(홈 → 목적지 확인 → 기록 → 종료 → 카드 → 내 기록)의 단계 수와 혼란 지점.
- 시각 완성도: Pleos 토큰 준수, 다크/라이트, 좁은 창(분할 화면) 대응, 흑백 이미지 같은 미완성 요소.
- `app/src/main/res`, Compose UI 코드, `docs/verification/mockup-ui` 화면 자료를 근거로 쓴다.

### 3. 모빌리티 사업개발 임원 (현대차그룹 모빌리티 서비스 사업부 상무)

중점: 사업성.
- 타깃 고객이 누구인가(드라이브 여행족, 출퇴근자, 가족 등). 문서에 정의되어 있는가.
- 반복 사용 동기: 한 번 쓰고 끝나는 기능인가, 매 주행 열 이유가 있는가. Retention을 만드는 장치(기록 누적, 카드 공유, 커뮤니티 코스).
- 수익 모델과 확대 경로: 커뮤니티, 제휴(관광, 충전, 주차), 데이터 사업, Pleos App Market 내 위치.
- 예상 MAU와 Retention을 기획서에 어떻게 제시해야 설득력이 있는지, 현재 근거로 가능한 추정치.
- 경쟁 서비스(티맵 주행 기록, 카카오내비, Strava 류, 차량 제조사 커넥티드 앱)와의 차별점.

### 4. 오픈이노베이션 심사위원 (스타트업 액셀러레이터 파트너, 외부 심사위원)

중점: 창의성, 문제 정의.
- 해결하려는 Pain Point가 실제로 존재하고 절실한가. 문제 정의가 문서에 명확한가.
- 아이디어의 새로움: 드라이브 카드, 경로 다시 보기, QR 휴대폰 전달, 구간 기록이 기존 서비스 대비 새로운가, 조합의 가치가 있는가.
- 스토리텔링: 2차 PT와 시연 영상에서 3분 안에 '와' 하는 순간을 만들 수 있는가. 그 장면은 무엇인가.
- 범위 관리: 기능이 너무 많아 핵심이 흐려지지 않았는가. 빼야 할 것과 강조할 것.
- 아이디어 특별상과 숏폼 챌린지 가능성.

### 5. Pleos App Market 검수·정책 담당 (앱 마켓 품질 및 개인정보 보호 검수관)

중점: 반려 위험, 제출 요건, 실제 동작과 주장의 차이. 감점 요인을 찾는 역할이다.
- 마켓 반려 사유 점검: 최상단 Back 동작(`moveTaskToBack`), 주행 중 화면 정책, Distraction Optimized 선언, 불필요한 퍼미션(`AndroidManifest.xml`).
- 개인정보: 위치·경로 데이터 저장과 전송, 외부 지도(OpenFreeMap) 통신, QR로 보내는 데이터의 범위, 커뮤니티 공개 시 500m 자르기와 동네 단위 표시가 실제 코드에 구현되었는가.
- 저작권: 앱에 들어간 사진과 지도 타일의 출처와 사용 권한.
- 제출 요건 충족: `apk/` 폴더와 파일명 형식, README 필수 항목, release 서명, `keystore.properties`나 비밀 값이 git에 들어갔는지(`git log`, `.gitignore` 확인).
- release 빌드에서 목업과 시뮬레이션이 정말 빠지는가. 실제 데이터가 아닌 값이 표시 없이 나오는 곳이 있는가.
- README의 '남은 작업'에서 마감 전에 반드시 닫아야 하는 것.
