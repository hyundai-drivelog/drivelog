## 3. 심사위원별 보고서

### 3.1 Pleos 플랫폼 기술 심사위원

차량 신호와 내비를 실제 기록 흐름에 결합한 완성도는 경쟁권이지만, 확장 모드의 장기 기록 보존과 실행 검증을 보완해야 한다.

**담당 점수 7.6/10 — 상위 10팀 경쟁권.** 차량특화성 7.7: 기어·주행 제한을 화면과 저장 흐름에 연결했다. 창의성 6.5: 카드·방문 스탬프의 조합은 명료하지만 개별 기능의 독창성은 제한적이다. 기술 활용성 7.6: AAOS·Pleos 역할 분리와 복구·오프라인 처리가 충실하다. 사업성 5.5: 연동 구현은 확장 근거지만 실제 운영 검증은 부족하다.

강점은 네 가지다.

1. 표준 기어·주행 제한·에너지는 AAOS에서, 내비·위치·음성은 Pleos에서 처리한다(`VehicleStateMonitor.kt:49`, `:80`, `:98`; `PleosCarPlatform.kt:209`, `:229`).
2. STT 결과는 검색창에만 넣고 명시적인 찾기 이후 내비 검색을 연다. 경로 개요도 `OverviewRoute`를 사용한다(`CarViewModel.kt:190`, `:373`; `PleosCarPlatform.kt:479`).
3. 저장 완료까지 복구 파일을 유지하며 위치 단절 재시도와 이상 이동 필터가 있다(`CarViewModel.kt:502`, `:548`; `Recorder.kt:184`, `:211`).
4. 차량·서버 스탬프는 0.1km 이상·위치 두 점 이상·최근접 명소 1km 이내 기준을 공유한다. 카탈로그 검사도 17지역·56곳 동기화에 통과했다(`StampPlaces.kt:66`, `:70`; `StampCollection.java:32`).

위험은 네 가지다. **높음:** 연결 모드에서 서버 최근 200건 응답으로 차량 전체 여정을 덮어써 오래된 로컬 기록과 스탬프가 목록에서 사라질 수 있다(`JourneyStore.kt:197`, `JourneyService.java:401`). **보통:** 홈 월 합계는 시뮬레이션을 포함하면서 표시하지 않는다(`HomeScreen.kt:74`). **보통:** 차량 테스트는 규칙 중심이며 저장 실패·재시작·서비스 연결·동기화 경쟁 상태의 자동 검증 근거가 부족하다(`app/src/test/`). **보통:** 인계의 브랜치·외부 빌드 경로와 체크아웃이 달라 검증 추적이 어렵다.

PT 질문과 답변 방향:

- **휴대폰으로도 가능한가?** 차량 제한·기본 내비·백그라운드 기록이 연결되는 실제 흐름을 보여준다.
- **GPS가 틀리면?** 마지막 관측 위치와 1km 반경의 한계, 단절 안내, 실차 주차 위치 검증 계획을 밝힌다.
- **200건 이후도 보존되는가?** 서버 스탬프 전체 조회와 차량 덮어쓰기 문제를 구분하고 병합·페이지 조회 및 회귀 검증으로 답한다.

실차 GPS·도착 콜백·실측 에너지·실제 휴대폰 연결은 미확인이다. 차량 테스트는 기존 결과 재사용이고, 서버 45개는 이번 실행에서 통과했다.

### 3.2 차량 HMI·UX 디자인 책임자

주행 중 정보 절제와 정차 후 보상은 설득력 있지만, 사용자에게 보이는 설명과 검증 증거의 신뢰성을 먼저 정리해야 한다.

**담당 점수 7.3/10 — 상위 10팀 경쟁권.** 차량특화성 7.3: 주행 제한·기어를 화면 흐름에 결합했다. 창의성 6.4: 카드와 도장 조합은 이해하기 쉽지만 차별성 검증은 부족하다. 기술 활용성 7.4: 내비 위임·지도·복구가 경험에 연결된다. 사업성 5.3: 반복 이용을 입증하는 사용자 결과는 미확인이다.

강점은 네 가지다.

1. 진입 경로와 무관하게 주행 중 기록 또는 잠금 화면을 선택하고 정차 판단에 UX 제한과 기어를 함께 쓴다(`CarApp.kt:30`, `CarViewModel.kt:161`).
2. 기록 화면의 종료·내비 버튼은 정차 중에만 보이고 장소·분 단위 시간·거리의 계층이 명확하다(`CarScreens.kt:186`, `:215`).
3. 작은 버튼도 64dp 규격이며 좁은 종료 화면은 전체 폭 세로 버튼으로 바뀐다(`CarComponents.kt:153`, `CarScreens.kt:324`).
4. 로딩 중 작업 이름과 처리 상태를 접근성 정보에 유지하고 홈 스탬프 진입에도 버튼 역할과 읽기 설명이 있다(`CarComponents.kt:224`, `HomeScreen.kt:78`).

위험은 다섯 가지다. **높음:** 월 합계에 시뮬레이션 포함 안내가 없다(`HomeScreen.kt:74`, `PlaceScreens.kt:524`). 카드의 표시는 이 오해를 해결하지 않는다. **높음:** 소개는 서버 미저장을 단정하지만 연결 화면에 서버 전송 설명이 부족하다(`WelcomeScreen.kt:71`, `CarScreens.kt:353`). **높음:** 실제 분할 창 종료 화면·TalkBack·실차 글자 크기는 미검증이다(`PLEOS_UX_BENCHMARK_2026-11-10.md` 통합 결과). **보통:** 내비에서 돌아와 기록을 시작하는 흐름은 이탈 가능성이 있고 복귀 안내 명칭도 정리가 필요하다(`CarViewModel.kt:386`). **보통:** 홈 지도·아이콘·구분선 금지 가이드와 실제 코드가 다르고 같은 가이드 안에서도 허용 여부가 충돌한다(`HomeScreen.kt:59`, `:119`, `:164`; 설계 원칙 §10).

PT 질문과 답변 방향:

- **휴대폰 기록 앱과 무엇이 다른가?** 차량 신호·내비로 운전 중 조작을 줄이는 흐름으로 답한다.
- **내비에서 돌아오지 않으면?** 현재 복귀 안내와 측정할 시작 이탈률을 제시한다.
- **접근성과 좁은 창은 검증됐는가?** 코드 대응과 실제 확인 범위를 나누고 분할 창·TalkBack 영상을 보인다.

`design-home.png`는 부산 8곳·이전 배치이므로 현재 홈의 증거가 아니다. 실제 기기의 대비·물리 크기·전환 지연은 미확인이다.

### 3.3 모빌리티 사업개발 임원

운전자에게 남는 여행 기록은 이해하기 쉽고 사업계획도 갖췄지만, 돈을 낼 고객과 반복 이용의 근거는 가설 수준이다.

**담당 점수 5.4/10 — 평범.** 차량특화성 7.4: 차량 신호·목적지 설정을 기록에 묶었다. 창의성 6.4: 조합은 명확하나 독점적 우위로 보기 어렵다. 기술 활용성 7.3: 실제 연동이 확장 근거다. 사업성 5.4: 구매 의사와 이용 지표는 미검증이다.

강점은 세 가지다.

1. 무료 사용자와 비용을 내는 지자체·관광지·렌터카 고객을 구분했다(`BUSINESS_PLAN.md` §3).
2. 매출·MAU에 계산식과 가정 표시를 붙여 실적처럼 오인시키지 않는다(§4~5).
3. 기록 저장·전송과 기록 기반 스탬프 재계산이 실제 구현돼 있다(`JourneyStore.kt:117`, `:159`, `:180`; `StampCollection.java:28`). 부산 시범→제주 렌터카 순서도 초기 영업 범위를 좁힌다(§6).

위험은 여섯 가지다. **높음:** 지자체 연 3천만~5천만원, 렌터카 월 1천원에 구매 담당자·예산·유사 계약 근거가 없다(§4). **높음:** QR 유입 구현됨·서버비 거의 0·경로 비수집 설명이 현재 연동과 충돌한다(§2·5·8; `JourneyStore.kt:137`, `:180`). **높음:** 연결 해제는 로컬 기록을 유지하고 다음 연결은 전체 기록을 큐잉하므로 공용·렌터카에서 이전 운전자 기록이 새 계정으로 넘어갈 가능성이 있다(`JourneyStore.kt:142`, `:150`). **보통:** 렌터카 이용 건수와 고유 사용자를 합산하고 중복 제거 정의가 없다(§5). **보통:** 4주 재방문율 25~35%·월 스탬프 1.5개는 관찰 결과가 아닌 목표다. **보통:** komoot·제조사 앱 비교가 부족하고 설치 장벽 없음은 설치율을 곱하는 MAU 모델과 설명이 맞지 않는다.

PT 질문과 답변 방향:

- **누가 얼마에 사는가?** 첫 구매 담당자·예산·시범 범위·성공 조건을 제시한다.
- **참여율이 높다는 증거는?** 기존 방식 대비 기록 시작률·방문 완료율·재방문율을 보인다.
- **렌터카 반납 후 기록은 누구 것인가?** 대여 세션별 소유권·연결 해제·삭제·동의를 설명한다.

### 3.4 오픈이노베이션 심사위원

운전자가 놓친 여행의 기억을 차량 신호와 연결한 조합은 설득력 있지만, 문제의 절실함과 반복 사용 이유는 검증되지 않았다.

**담당 점수 6.4/10 — 평범.** 차량특화성 7.6: 내비·기어·제한을 흐름에 묶었다. 창의성 6.4: 기능의 최초성보다 조합 완성도가 강점이다. 기술 활용성 7.4: SDK가 핵심 경험에 있다. 사업성 5.3: 구매·재방문 증거가 부족하다.

강점은 세 가지다.

1. 운전자와 동승자의 여행 경험 차이를 페르소나로 구체화했다(`PRODUCT_BRIEF.md` §1).
2. 목적지 확인에서 안내·기록을 명시적으로 시작하고 주행 중 기록·잠금 화면만 허용한다(`CarViewModel.kt:439`, `CarApp.kt:30`). 차량 앱인 이유가 흐름에서 드러난다.
3. 도장은 기록에서 계산해 별도 체크인 없이 카드와 방문 기록을 남긴다. 전국 56곳 카탈로그와 삭제 시 재계산도 목업을 넘어선다(`StampPlaces.kt:68`, `:77`).

위험은 다섯 가지다. **높음:** 운전자에게 남는 것이 없다는 문제의 크기를 입증한 인터뷰·관찰·이용 결과가 없다(`PRODUCT_BRIEF.md` §1). **높음:** 차별점인 서버 없는 QR 전달이 Android·서버 확장 구조와 맞지 않는다(§3·5; `JourneyStore.kt:142`, `:182`). **보통:** P로 바꾸면 카드가 만들어진다는 표현은 수동 저장과 조건부 자동 저장을 압축해 오해를 만든다(`CarScreens.kt:221`, `:255`; `CarViewModel.kt:439`). **보통:** 스탬프는 마지막 GPS 지점 반경 1km의 최근접 명소 판정이므로 입장·체류 인증이나 강한 부정 방지로 과장하면 안 된다(`StampPlaces.kt:57`, `:68`). **보통:** 효율·구간·세차·커뮤니티·모바일까지 설명하면 핵심이 흐려진다.

PT 질문과 답변 방향:

- **휴대폰으로도 가능한데 왜 차인가?** 차량 신호·내비와 연결된 시작과 안전 전환을 보여준다.
- **다음 달에도 열 이유는?** 기능 목록보다 이용자의 재방문 관찰을 제시한다.
- **기존 기록·스탬프 앱과 무엇이 다른가?** 최초성 주장보다 운전자 조작을 늘리지 않고 결과를 남기는 흐름으로 답한다.

사용자 반응·경쟁 제품 전체 기능·실차 판정은 미확인이다. 현재 APK도 없어 release 경험을 새로 검증한 것은 아니다. 발표는 목적지→주행 제한→정차 저장→경로 카드·첫 도장에 집중하고 확장은 보조 자료로 둔다.

### 3.5 Pleos App Market 검수·정책 담당

화면 제한과 debug 분리는 개선됐지만, 제출 바이너리와 개인정보 설명을 현재 제품에 맞춰야 검수 준비가 됐다고 볼 수 있다.

**담당 점수 5.6/10 — 평범.** 차량특화성 7.2: 차량 상태와 화면이 연결된다. 창의성 6.1: 조합은 명확하나 차별성 검증이 부족하다. 기술 활용성 7.2: 안전 제한·내비 위임 구현이 있다. 사업성 5.1: 확장에 필요한 동의·사용자 분리가 미완성이다. 확장 위험을 기본 APK 실행 결함으로 계산하지 않았다.

강점은 세 가지다.

1. 주행 중 기록·잠금 화면만 선택하는 공통 진입점이 있다(`CarApp.kt:30`).
2. 진단·커뮤니티·휴대폰 미리보기 진입을 debug 조건으로 제한한다(`CarApp.kt:44`, `:87`, `:142`, `:144`).

PT 질문과 답변 방향:

- **어떤 기록이 어디에 얼마나 저장되는가?** 모드별 데이터 흐름·삭제·동의를 제시한다.

지도 출처는 실제 컴포넌트에 있고 홈 썸네일까지 연결된다(`RouteMap.kt:200`, `DriveRouteArt.kt:214`). 작은 크기 가독성과 제공자 요건 충족은 미확인이다. 실제 APK·마켓 승인·외부 처리방침·라이선스 원본은 미확인으로 최종 반려나 법적 위반을 확정하지 않는다.

### 5.1 연결 모드의 장기 기록 보존

`JourneyStore.kt:197`은 서버 응답으로 전체 여정을 교체한다. `JourneyService.java:401`의 응답은 `LIMIT 200`이다. 두 구현이 결합되면 201건 이상의 계정에서 오래된 차량 로컬 기록·스탬프가 목록에서 사라질 가능성이 있다.

서버 데이터 삭제를 확인한 것은 아니다. 서버 스탬프 조회는 전체 기록을 대상으로 하므로 차량 목록과 서버 스탬프가 달라질 수도 있다. 실제 201건 재현은 하지 않았다. 기본 제출 모드에는 적용되지 않는 확장 모드 위험이다.

### 5.2 사용자 전환 시 과거 기록 전송

`JourneyStore.kt:137`의 최초 연결 처리는 기존 기록을 큐잉하고, `:150`의 연결 해제는 로컬 기록을 유지한다. 따라서 같은 차량을 다른 계정에 연결하면 이전 기록이 새 계정으로 전송될 가능성이 있다. 공용·렌터카에서 사용자별 저장과 대기열 분리가 필요하다. 정적 코드로 확인한 위험이며 실제 전송 재현은 하지 않았다.

### 5.3 지도 출처의 판단 범위

지도 출처가 전부 없다는 지적은 현재 코드와 맞지 않는다. `RouteMap.kt:200`, `DriveRouteArt.kt:214`, `RouteMapCache.kt:334`에 표기가 있고 홈 썸네일도 같은 렌더링 경로를 사용한다. 다만 상수는 `© OpenMapTiles © OpenStreetMap`이며 작은 썸네일의 가독성·링크·OpenFreeMap 제공자 조건의 완전 충족은 미확인이다. [OpenFreeMap 공식 예제](https://openfreemap.org/quick_start/)와 대조해야 한다.
